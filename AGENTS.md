## Note writing

Apply the shared conventions to both note types, then use the rules for the type being written. Theory/math learning notes develop the mathematical understanding; implementation companions explain working software that applies it. Theory-specific derivation and quiz requirements do not apply to implementation companions.

### Shared conventions

1. **Prerequisite discipline:** Write timeless, teacher-led notes for a reader who has read only the declared prerequisite notes and the preceding parts of the current note. Assume no other textbook knowledge, robotics convention, implementation knowledge, or future chapter content. Keep an opening prerequisites section limited to knowledge the reader needs before starting the chapter: cite the owning prior section and briefly recall the exact result needed, or supply the missing explanation in its appropriate note type before use. Do not put chapter scope, exclusions, construction status, postponed topics, or lists of material introduced later in the prerequisites section. Introduce assumptions and validity conditions where they first matter.
2. **Explicit, economical mathematical notation:** Define every mathematical symbol, set, space, index, superscript, subscript, block, and operator at first use, including meaning, type, and dimensions. Name mathematical objects and symbols together; avoid vague referents when more than one object is in scope. For a mapping, state its input, output, defining relation, and spaces. Reuse project notation, minimise simultaneous representations, and map textbook notation to project notation. Code identifiers follow the snippet-first rule for implementation companions.
3. **Representation and summary discipline:** Distinguish physical objects, states, and motions from their coordinate descriptions and mathematical operators. When several representations describe the same object or motion, state their relationship and the question each answers. Place symbol tables, memory aids, and other summaries only after their contents have been introduced; summaries consolidate rather than introduce material.
4. **Frames, units, and conventions:** For every frame-dependent quantity, state what it describes, relative to which reference, and in which frame its components are expressed. Do not describe a quantity as measured by the body when it is only expressed along body axes. Declare units, sign conventions, component order, active or passive interpretation, and multiplication direction before relying on them, and keep quantities with different units separate in explanations and validation.
5. **Simple, concrete explanations:** Use common words, short direct sentences, and concrete subjects and actions. Explain which object is involved, what is calculated or changes, and why. Make the first draft complete enough that review is not required to supply missing definitions, setup, or reasoning appropriate to the note type.
6. **Clean learning scope:** Omit project status, phase questions, progress markers, local source paths, drafting or construction status, implementation-status commentary, lists of postponed topics, and forward-looking chapter-boundary prose. Keep live status in the owning checklist. Explain a limitation only where it changes mathematical meaning or correct use; do not add a standalone limitations section without such a reason.
7. **Review cadence:** Write one small learning or implementation block at a time and wait for user review before continuing, unless the user explicitly requests a larger batch.
8. **Fast interactive review edits:** When the user is reviewing an existing note and requests a local update, rewrite, reorder, simplification, or complement, edit it immediately and check only the changed passage's LaTeX or Quarto syntax. Do not re-consult textbooks, invoke review skills, run a full-book render, link check, test suite, broader audit, or registry update for each local edit. Accumulate deeper coherence, notation, cross-reference, and rendering checks until the whole section is drafted or its review is complete, unless the user asks sooner. A new whole section or an expansion beyond the reviewed passage uses normal verification.
9. **Mathematics and source formatting:** In Quarto notes, use `$...$` for inline mathematics and `$$...$$` for display mathematics. Keep each prose paragraph on one source line. Use line breaks only for headings, lists, tables, code blocks, and display mathematics.
10. **Quarto structure and references:** Keep `number-sections: true` and `number-depth: 3`; let Quarto number chapter titles, `##` sections, and `###` subsections, and leave `####` headings unnumbered by depth. Do not hard-code section numbers or write numeric prefixes in headings. Where present, mark purpose, prerequisites, dependency maps, quick tests and answers, cumulative tests, references, and supplemental checks with `{.unnumbered}`. The note-type rules determine which of these belong in a chapter. Give referenced headings stable `{#sec-...}` labels and cite them with `@sec-...`.
11. **Chapter registries:** After a chapter is complete, add only notation first introduced by that chapter to `notes/notation.qmd`, preserving chapter order and chapter cross-references. After the chapter is reviewed, add only its newly defined technical terms to `notes/glossary.qmd`, keeping entries alphabetical, concise, and linked to their first defining sections. Do not pre-populate unfinished chapters or duplicate entries between the two registries.
12. **Supporting example callout format:** When a useful complementary example supports already-explained material, use the template below. The note-type rules determine the example's content; a callout is not required for every section. If an example is the main learning content of an entire section or subsection, write it as ordinary section prose instead of wrapping the whole section in a callout.

    ```markdown
    ::: {.callout-note title="Example: <descriptive title>" appearance="simple" icon=false}

    <State what the example demonstrates, then give its setup, worked content, and interpretation.>

    :::
    ```

### Theory/math learning notes

1. **Purpose-led dependency order:** Begin each learning block with the physical, mathematical, or numerical question it answers, why the answer is useful, the known inputs, and the required output. Present one dependency-ordered chain: purpose → prerequisite results → derivation with new intermediate quantities introduced only when needed → interpretation → application. Do not preview unexplained equations and then repeat their derivation later; signpost the plan in words and derive each result once in its logical place.
2. **Terms and motivated definitions:** Explain the underlying idea in simple English before naming a technical term. Define the term and any symbol attached to it at first use, using only terminology already explained. State why the definition has its chosen form, what each component represents, and what calculation or distinction it enables. Identify a definition or convention as a deliberate choice rather than presenting it as a derived fact.
3. **Connected equation derivations:** Before an equation, state the result or problem from which it follows and why it is being calculated. Derive every non-definition from preceding definitions or an explicitly cited prerequisite, showing intermediate algebra, assumptions, and valid domain. Afterward, name the result and explain its mathematical meaning, physical meaning, intended use, and essential validity conditions. Derive equivalent formulas and explain why the new form is useful. When selecting matrix entries or components, write out the source structure and show how each selected component is obtained.
4. **Textbook-grounded drafting:** Before drafting a new mathematical, physical, algorithmic, or theoretical learning block, consult the primary chapter routed by `textbooks/INDEX.md`. For a major concept, also consult a supporting source when it supplies an independent derivation, modelling viewpoint, or implementation guidance. Preserve dependency order and depth, cite sources bibliographically, and do not copy their wording or replace current official software guidance with outdated textbook instructions.
5. **Contrasts and proofs:** Define easily confused terms together and state their difference explicitly. Before a proof, state exactly what it will establish and outline its logic. For equality of sets, mappings, or characterisations, prove both directions and explain why both are required.
6. **Purposeful mathematical examples:** Place physical, geometric, or numerical examples where they demonstrate an already-stated purpose, derivation, validity condition, or failure. State what the example shows before calculating it. After an abstract definition, give the smallest concrete example that instantiates every new symbol and shows its meaning. Do not substitute an example for the general explanation or present it before its mathematical prerequisites.
7. **Retrieval tests:** After each major concept, test recall, explanation, derivation, application, and any validity condition essential to correct use. Include a cumulative chapter test with answers or hints. These quizzes belong to theory/math learning notes, not implementation companions.

### Implementation companions

1. **Block structure and opening:** Organise each block around one mathematical operation or coherent data representation, not a file-by-file tour. Use mathematical summary → concise pseudocode when needed → essential code snippets → code explanations, with a usage example only when useful. Before a long or multi-stage implementation, provide pseudocode showing the main stages, ordering, important checks, and failure outcome; do not translate every source line into pseudocode. Do not add a purpose section at the top of an implementation note; after any needed prerequisites, begin the first implementation block.
2. **Mathematical summary and numerical reasoning:** Briefly state what the operation computes, its governing equation, inputs, outputs, and essential assumptions, including dimensions, units, and frames where relevant. Cite the owning theory section instead of repeating its derivation. Include a concise implementation-specific derivation when needed to explain a numerical choice, such as the sign of Kahan compensation. Substantial new theoretical foundations belong in the theory notes.
3. **Code before explanation:** Show classes, functions, members, local variables, and library operations in a code block before discussing their names or syntax in prose. Before the snippet, describe the mathematical intent without introducing unseen code identifiers. Explain the visible code afterward; do not make the reader reconstruct code from prose.
4. **Selective, faithful implementation excerpts:** Show code that explains the mathematical operation or a meaningful implementation decision, not every line needed to compile the production function. Show complete small classes and functions when their full implementation is useful; otherwise use clearly labelled production excerpts with enough declarations and setup to understand them. Preserve essential mathematical and numerical logic and match the working implementation's names, types, and retained operations. Omit repetitive guards, exception-message construction, and boilerplate when prose can explain them clearly. Identify every omission and any assumed prior validation; never present an excerpt as a complete replacement function. Distinguish production excerpts, usage examples, schematic syntax, and alternative spellings.
5. **Contextual syntax explanation:** Show the working snippet before explaining unfamiliar language syntax or library operations that appear in it. For a new C++ function, method, or feature that needs more than a brief explanation, use short lists in this order: explain the feature itself through its general syntax, inputs, behaviour, result, and essential requirements; then explain its use in the displayed snippet through the relevant arguments, captures, types, return values, ownership, and lifetime. Do not require lists for every syntax item; use brief prose when sufficient. Introduce language or software-engineering terms only when the visible code gives them a concrete purpose, and avoid repetitive line-by-line paraphrase.
6. **Equation-to-code mapping and representation:** After the relevant snippet, identify each non-obvious code variable with its mathematical quantity. Explain indexing, dimensions, storage order, scalar types, units, and conventions where they affect interpretation. Distinguish the mathematical object from its storage representation and explain owned values, copies, moves, and borrowed views when they affect use.
7. **Selective usage examples:** Include an example only when it is helpful or important, not for every section. A supporting usage callout should show a small input, a call to the implemented operation, an independently expected result, and its interpretation. Prefer ordinary API usage to test-framework machinery unless the test syntax is itself important. Use ordinary section content when the usage example is the main subject of the subsection.
8. **Cycle-wide data-flow diagram:** After explaining the classes and functions for one mathematical implementation cycle, add one “How the classes and functions connect” section for that cycle. Use compact plain-LaTeX diagrams with boxed, multiline contents and centred arrows. Pair relevant code names with essential equations to show inputs, construction, stored data, evaluation, and outputs. Distinguish fixed model data from per-call inputs, separate inputs from derived quantities, and ownership from calculation flow where relevant. Use separate construction and evaluation diagrams when clearer. Consolidate only previously explained material, keep accompanying prose brief, and summarize repetitive validation rather than drawing every safeguard.
9. **Essential validation and verification meaning:** Explain checks that establish mathematical validity, protect numerical calculations, or determine correct API use. Summarise repetitive validation code in prose, including the valid input domain and failure behaviour, instead of cataloguing every rejection branch. Retain checks beside a calculation when they explain a numerical risk, such as overflow after screw scaling. Omitting safeguards from a displayed excerpt does not remove them from production code or its contract. Briefly explain the distinct mathematical properties established by representative automated tests; include test snippets only when they teach something important. Retain numerical cautions and known failure behaviour that affect correct use; keep exhaustive acceptance lists and interpreted audit findings in their owning project documents.
10. **No quizzes:** Do not include retrieval questions, quick checks, cumulative quizzes, or their answer sections in implementation companions. This does not remove automated implementation tests, the theory-learning gate, or the requirement that the learner understand the code.
11. **Retrospective sources and focus:** Ground the companion in the working code, its specification, relevant tests, and the owning theory notes. Use authoritative software documentation to resolve uncertain language or library semantics. Describe durable implementation decisions, not speculative interfaces or future architecture. Explain build and tooling details only when they are the subject of the block.
12. **Previously learned syntax:** Do not repeat generic explanations already established in the declared prerequisite notes or preceding sections. Briefly cross-reference the owning explanation when useful. Explain a new use, subtle behaviour, or operation-specific consequence where it matters, and address an identified misunderstanding. Distinguish previously introduced material from material that has been reviewed and understood; do not infer mastery merely from its presence in an earlier note.
13. **Purposeful comments:** Use comments in displayed code to mark major phases or explain a non-obvious reason. Do not repeat the pseudocode line by line or narrate obvious syntax. Identify teaching annotations when they differ from production comments.

## Capability workflow

1. **Project-wide capability cycle:** Move one active implementation-sized mathematical, scientific, or engineering capability through learn and write → review and quiz → create or extend the specification → implement with verifying tests → write the retrospective implementation companion → close. A phase contains several such cycles. Engineering may begin when the active cycle's prerequisite theory has been reviewed and its minimum specification is ready; unrelated chapter or phase theory need not be complete.
2. **Learning gate:** Draft only the theory needed by the active cycle, in dependency order. The user reviews the learning block and completes its relevant retrieval questions. Correct blocking misconceptions before extending the specification. A whole chapter need not be complete unless the active cycle depends on its remaining material.
3. **Specification gate:** Before production implementation begins, create or extend the owning specification with the active cycle's requirements, inputs, outputs, frames, units, conventions, validation, failure behaviour, exclusions, and independent acceptance cases. Preserve approved shared contracts unless evidence justifies a deliberate revision, and do not speculate about interfaces or requirements belonging only to later cycles.
4. **Implementation and verification gate:** Implement the smallest complete operation and develop its focused tests alongside it. Verify normal cases, boundary cases, invalid inputs, and governing mathematical properties, using independent analytic results where practical. Compile or test each buildable block. This stage is complete only when the focused tests pass and the user can explain the important syntax, equation-to-code mapping, frames, units, conventions, and failure behaviour.
5. **Retrospective companion gate:** Write the implementation companion section only after the active implementation and focused tests work and the user understands them. Create the companion file when its first substantive retrospective section is ready; do not create an empty or speculative placeholder.
6. **Closure gate:** Before closing the cycle, review the retrospective companion section, run the relevant package build and predefined acceptance tests, inspect the affected files and diff, check required documentation or render output, and link the evidence from the owning live checklist. Run broader quality gates only at their declared stability checkpoints.
7. **Artifact boundaries:** Keep theory and retrieval checks in learning notes, durable implementation know-how in companion notes, requirements and acceptance criteria in specifications under `docs/`, production code and deterministic checks in `ros_ws/src`, and reproducible commands in the owning package README or environment documentation. Keep detailed experiment results and manifests with their owning artifacts, and contract findings or claim boundaries in the owning specification. The live checklist records a concise verification outcome, limitations or unresolved findings, and links to the existing evidence without duplicating it. Preserve reproducibility, negative results, and the reasoning needed to support claims; a separate report is not a closure requirement. Do not create standalone verification, milestone, benchmark, or closure reports unless the user explicitly requests one.
8. **Cycle tracking:** Make each live checklist identify its active capability, active cycle, active stage, and exactly one active task. `CHECKLIST.md` owns the main robotics frontier and `INTELLIGENCE_CHECKLIST.md` owns the parallel intelligence frontier. Represent the six stages in dependency order, close one cycle before activating the next within its owning checklist apart from explicitly declared non-blocking work, and converge rather than duplicate when the main frontier reaches an early intelligence artifact. Keep queued capabilities as concise artifact-level outlines and decompose them into cycles only when they approach activation.
9. **Scope and dependency discipline:** Follow the Understand / Implement / Integrate commitments and release dependencies in `PLAN.md`. Phase and capability identifiers describe ownership, not a mandatory numerical execution order. A completed cycle may serve its consumer before unrelated work in its chapter, capability, phase, or parallel track closes. Give a shared unfinished cycle exactly one checklist owner. An educational implementation acquires application integration only when the plan or a reviewed selection record requires it.
10. **Bounded experiments:** Before a research campaign, freeze its question, contenders, data and compute budgets, independent training seeds, evaluation, tuning limit, and stop conditions under the `PLAN.md` experiment contract. A pilot informs numerical budgets. A supported negative result can satisfy the declared evidence gate; broken implementation, inadequate evaluation, or an exhausted budget alone cannot.

## Document ownership

1. **Programme plan:** `PLAN.md` is the stable source for the learning programme's purpose, scope, architecture, milestone dependencies, phase learning goals, capstone products, and completion criteria. Do not put live status or task checkboxes in it.
2. **Live checklists:** `CHECKLIST.md` is the live progress tracker for the main robotics frontier and `INTELLIGENCE_CHECKLIST.md` is the live tracker for the parallel intelligence-foundations frontier. Keep a compact status table in each, expand only its current capability region into ordered artifact-level tasks, name exactly one active task per checklist, link rather than copy evidence, and never let the parallel tracker close a main phase without its required robotics evidence.
3. **Rolling detail:** When a main phase closes, preserve a concise acceptance conclusion and links to the existing evidence in `CHECKLIST.md`, reduce its working detail to one status row, and expand the next phase selected by the plan's dependencies. When an intelligence milestone closes, preserve its evidence through `INTELLIGENCE_CHECKLIST.md`. At each cross-track handoff, link accepted cycles and transfer shared unfinished work to one owner; retire the parallel tracker as merged only when all its remaining independent work has been completed or explicitly transferred to the owning main phases. Git history preserves completed working detail.
4. **Historical trackers:** Files marked as legacy archives are non-authoritative and must not be used to decide current work.

## Coding

1. **Learner-authored, code-led implementation:** Organise implementation around one mathematical concept per cycle. A cycle may contain several sequential code blocks across several conversations, but keep each conversation manageable and review each block before continuing. The user writes production source, headers, tests, and build files; explain, review, and diagnose them, but do not edit implementation files unless the user explicitly requests a particular change.
2. **Cycle brief:** During learner-authored implementation, before the first code block, give only the mathematical question, governing equation or engineering requirement, concrete inputs and outputs with frames and units where applicable, one normal example, any important failure or boundary case, the expected sequence of code blocks, and the focused verification command. Do not front-load speculative architecture or unfamiliar software terminology.
3. **Contextual explanation:** After each code block is visible, explain the language syntax and software-engineering terms that occur in that block and connect its operations to the governing equation or requirement. Introduce a term when the code creates a concrete reason for it, not as an abstract catalogue before implementation.
4. **Equation-to-code names:** Follow the equation-to-code mapping rule under Implementation companions when writing retrospective notes. During implementation teaching, likewise connect each non-obvious code variable to its mathematical quantity after showing the code.
5. **Feedback loop:** Compile the smallest complete target or run the single relevant test whenever the current blocks form a buildable step. If a block is intentionally incomplete, inspect it and defer compilation only until the next block completes that step. Diagnose failures from their exact output and make the smallest understandable correction before continuing.
6. **Mathematical-cycle verification:** Before closing a cycle, run focused tests for its normal cases, boundary cases, invalid inputs, and governing mathematical properties; then build and test the affected package and inspect the changed files. A cycle is complete only when the required code compiles, the focused tests pass, the user can explain the important syntax and equation-to-code mapping, and the retrospective companion section has been reviewed.
7. **Retrospective implementation companions:** After the active implementation and focused tests work and the user understands them, write the retrospective section using the Implementation companions rules under Note writing. Keep project exclusions in the specification; the companion records durable implementation understanding, not another theory lesson or quiz.
8. **Quality-gate cadence:** Do not invoke a C++ or Python quality-gate skill for teaching, terminology explanations, implementation-note drafting, routine learner-authored blocks, or ordinary focused compilation and tests. Invoke the applicable gate only at a stability checkpoint named in the owning live checklist, before capability closure, when the user explicitly requests it, or when a difficult defect requires a systematic audit.
9. **Necessity gate:** Add code only for a stated requirement that cannot be met more simply; avoid speculative features, abstractions, and dependencies.
10. **Traceability:** Ground every algorithmic or scientific component in a documented mathematical model. Trace infrastructure components to explicit engineering requirements.
11. **Design quality:** Keep modules single-purpose with clear names, types, units, assumptions, invariants, inputs, outputs, and failure behaviour. Keep configuration separate from logic.
12. **Test value:** Prioritise tests for project logic, requirements, edge cases, invariants, public contracts, integration boundaries, and previously observed defects. Do not test unchanged language or library behaviour, trivial data storage, generated boilerplate, or simple accessors unless they form a deliberate public contract or protect against a credible regression.
13. **Reproducibility:** Pin or document dependencies, control randomness, avoid hidden state, and record the configuration required to reproduce results.
14. **Operational quality:** Validate inputs, handle failures deliberately, use safe fallbacks, and add useful logging, telemetry, and timing information where operationally necessary.
15. **Modern C++20:** Project-owned C++ targets shall use ISO C++20 with compiler extensions disabled and correctly scoped CMake compile features. New or changed code shall prefer appropriate C++20 standard-library facilities, RAII, value semantics, explicit ownership, strong domain types, const-correctness, and narrow interfaces when they improve clarity or safety; avoid speculative modernization and behaviour changes made only to use newer syntax.
16. **Neural implementation ownership:** Keep project-owned neural training and inference in C++20 and LibTorch. Python may support independent numerical references, data generation, plots, orchestration, and external comparisons. If implementation effort becomes excessive, reduce the task, model, or comparison scope and reuse accepted library infrastructure; changing the authoritative learner language requires a deliberate programme revision.
