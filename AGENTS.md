# Project Rules

## Execution environment

1. **Authoritative checkout:** Treat `/home/maxwell/Repos/robotics_autonomous` in Ubuntu WSL2 as the repository.
2. **Run natively in WSL:** Perform repository reads, edits, Git operations, builds, tests, and renders with Linux executables and native Linux paths.
3. **Proportional verification:** For a newly drafted whole note section, a completed section-review batch, a specification or implementation change, or another substantive batch, run `git diff --check`, inspect the affected diff and source region, then run the relevant test or render. Activate the repository virtual environment before Quarto executes Python blocks, and remove generated files when they are not requested deliverables. A local note correction made during interactive user review follows the fast-review rule under Note writing instead.
4. **Keep textbooks read-only:** Read textbook sources from the repository-local `textbooks/` directory; never modify them.
5. **Read the project context:** Before project work, read `PLAN.md` for the programme purpose, scope, architecture, milestones, and phase outcomes, then read `CHECKLIST.md` for the current phase, active capability, ordered tasks, and evidence links. Work from `CHECKLIST.md`.

## Note writing

1. **Reader knowledge boundary:** Write timeless, teacher-led lessons for a reader who has read only the declared prerequisite notes and the preceding parts of the current note. Assume no other textbook knowledge, robotics convention, implementation knowledge, or future chapter content. When a prior note owns a prerequisite, cite its section and briefly recall the exact result needed here; otherwise explain the prerequisite before use. Make the first draft complete enough that review is not required to supply missing definitions, derivations, or reasoning.
2. **Purpose-led dependency order:** Begin each learning block with the physical, mathematical, or numerical question it answers, why the answer is useful, the known inputs, and the required output. Present one dependency-ordered chain: purpose → prerequisite results → derivation with new intermediate quantities introduced only when needed → interpretation → application and limits. Do not preview unexplained equations and then repeat their derivation later; signpost the plan in words and derive each result once in its logical place.
3. **Terms and motivated definitions:** Explain the underlying idea in simple English before naming a technical term. Define the term and any symbol attached to it at first use, using only terminology already explained. State why the definition has its chosen form, what each component represents, and what calculation or distinction it enables. Identify a definition or convention as a deliberate choice rather than presenting it as a derived fact.
4. **Connected equation derivations:** Before an equation, state the result or problem from which it follows and why it is being calculated. Derive every non-definition from preceding definitions or an explicitly cited prerequisite, showing the intermediate algebra, assumptions, and valid domain. Afterward, name the resulting mathematical item and explain its mathematical meaning, physical meaning, intended use, and failure or boundary cases. When introducing an equivalent formula, derive the equivalence and explain why the new form is useful. When a definition selects matrix entries or components, write out the source structure and show how each selected component is obtained.
5. **Explicit, economical notation:** Define every symbol, set, space, index, superscript, subscript, block, and operator at first use, including its meaning, type, and dimensions. Name mathematical objects and symbols together; avoid vague referents such as *it*, *this quantity*, or *the block* when more than one object is in scope. For a mapping, state its input, output, defining relation, and spaces. Reuse project notation instead of introducing aliases for an existing object, minimise the number of simultaneous representations, and map textbook notation to the project notation.
6. **Representation and summary discipline:** Distinguish physical objects, states, and motions from their coordinate descriptions and mathematical operators. When several representations describe the same object or motion, state their relationship and the question each representation answers. Place workflow summaries, symbol tables, and memory aids only after every symbol they contain has been defined; summaries must consolidate earlier material rather than introduce new notation.
7. **Frames, units, and conventions:** For every frame-dependent quantity, state what it describes, relative to which reference, and in which frame its components are expressed. Do not describe a quantity as measured by the body when it is only expressed along body axes. Declare units, sign conventions, component order, active or passive interpretation, and multiplication direction before relying on them, and keep quantities with different units separate in explanations and validation.
8. **Simple explanations and purposeful examples:** Use common words, short direct sentences, and concrete subjects and actions. Explain which object is involved, what is calculated or changes, and why. Place a physical, geometric, or numerical example where it demonstrates an already stated purpose, derivation, boundary, or failure; state what the example is intended to show before calculating it. Do not use an example as a substitute for the general explanation or force it ahead of mathematical prerequisites needed to understand it.
9. **Mathematics before algorithms:** Explain the mathematical model before algorithms or code, and connect each algorithmic step to the equation or assumption it implements. Use `$...$` for inline mathematics and `$$...$$` for display mathematics.
10. **Textbook-grounded drafting:** Before drafting a new mathematical, physical, algorithmic, or theoretical learning block, consult the primary chapter routed by `textbooks/INDEX.md`. For a major concept, also consult a supporting source when it supplies an independent derivation, modelling viewpoint, or implementation guidance. Preserve the required dependency order and depth, cite sources bibliographically, and do not copy their wording or replace current official software guidance with outdated textbook instructions.
11. **Contrasts and proofs:** Define easily confused terms together and state their difference explicitly. Before a proof, state exactly what it will establish and outline its logic. For equality of sets, mappings, or characterisations, prove both directions and explain why both are required.
12. **Clean learning scope:** Omit project status, phase questions, progress markers, local source paths, and implementation-status commentary. Keep live programme and capability status in `CHECKLIST.md`.
13. **Retrieval tests:** After each major concept, test recall, explanation, derivation, application, and limitations. Include a cumulative chapter test with answers or hints.
14. **Review cadence:** Write one small learning block at a time and wait for user review before continuing.
15. **Fast interactive review edits:** When the user is reviewing an existing note and requests a local update, rewrite, reorder, simplification, or complement, edit it immediately and check only the changed passage's LaTeX or Quarto syntax. Do not re-consult textbooks, invoke review skills, run a full-book render, link check, test suite, broader audit, or registry update for each local edit. Accumulate deeper coherence, notation, cross-reference, and rendering checks until the whole section is drafted or its review is complete, unless the user asks sooner. A new whole section or an expansion beyond the reviewed passage uses normal verification.
16. **Source formatting:** Keep each prose paragraph on one source line. Use line breaks only for headings, lists, tables, code blocks, and display mathematics.
17. **Quarto structure and references:** Keep `number-sections: true` and `number-depth: 3`; let Quarto number chapter titles, `##` sections, and `###` subsections, and leave `####` headings unnumbered by depth. Do not hard-code section numbers or write numeric prefixes in headings. Mark purpose, prerequisites, dependency maps, quick tests and answers, cumulative tests, references, and supplemental checks with `{.unnumbered}`. Give referenced headings stable `{#sec-...}` labels and cite them with `@sec-...`.
18. **Chapter registries:** After a chapter is complete, add only notation first introduced by that chapter to `notes/notation.qmd`, preserving chapter order and chapter cross-references. After the chapter is reviewed, add only its newly defined technical terms to `notes/glossary.qmd`, keeping entries alphabetical, concise, and linked to their first defining sections. Do not pre-populate unfinished chapters or duplicate entries between the two registries.

## Capability workflow

1. **Dependency-gated cycle:** Move one active implementation-sized capability through learn and write → review → specify → implement and document → verify. Engineering may start when its prerequisite theory is approved and its minimum specification is ready; unrelated phase theory need not be complete.
2. **Artifact boundaries:** Create an implementation companion only when implementation begins; it may remain title-only until the first mathematical implementation cycle is complete. Keep theory and retrieval checks in learning notes, durable implementation know-how in companion notes, requirements and acceptance criteria in specifications under `docs/`, production code and deterministic checks in `ros_ws/src`, and interpreted phase or release conclusions in verification reports under `docs/reports/`. `CHECKLIST.md` records status and links to this evidence; it does not duplicate the evidence itself. Create a separate verification report for phase or release milestones, experiments, benchmarks, safety or performance claims, negative results, or results requiring interpretation.
3. **Implementation-cycle tracking:** During implementation, make the active `CHECKLIST.md` task one mathematical implementation cycle that includes its code, focused verification, learner review, and retrospective companion section. Do not make speculative implementation-note drafting a separate prerequisite to code.

## Document ownership

1. **Programme plan:** `PLAN.md` is the stable source for the learning programme's purpose, scope, architecture, milestone dependencies, phase learning goals, capstone products, and completion criteria. Do not put live status or task checkboxes in it.
2. **Live checklist:** `CHECKLIST.md` is the sole live progress tracker. Keep a compact programme-status table, expand only the current phase into ordered artifact-level capability tasks, name exactly one active task, and link rather than copy evidence.
3. **Rolling detail:** When a phase closes, preserve its conclusions in the owning phase verification report, reduce it to one status row in `CHECKLIST.md`, and expand the next phase there. Git history preserves completed working detail.
4. **Historical trackers:** Files marked as legacy archives are non-authoritative and must not be used to decide current work.

## Coding

1. **Learner-authored, code-led implementation:** Organise implementation around one mathematical concept per cycle. A cycle may contain several sequential code blocks across several conversations, but keep each conversation manageable and review each block before continuing. The user writes production source, headers, tests, and build files; explain, review, and diagnose them, but do not edit implementation files unless the user explicitly requests a particular change.
2. **Cycle brief:** Before the first code block, give only the mathematical question, governing equation or engineering requirement, concrete inputs and outputs with frames and units where applicable, one normal example, one important failure or boundary case, the expected sequence of code blocks, and the focused verification command. Do not front-load speculative architecture or unfamiliar software terminology.
3. **Contextual explanation:** After each code block is visible, explain the language syntax and software-engineering terms that occur in that block and connect its operations to the governing equation or requirement. Introduce a term when the code creates a concrete reason for it, not as an abstract catalogue before implementation.
4. **Feedback loop:** Compile the smallest complete target or run the single relevant test whenever the current blocks form a buildable step. If a block is intentionally incomplete, inspect it and defer compilation only until the next block completes that step. Diagnose failures from their exact output and make the smallest understandable correction before continuing.
5. **Mathematical-cycle verification:** Before closing a cycle, run focused tests for its normal cases, boundary cases, invalid inputs, and governing mathematical properties; then build and test the affected package and inspect the changed files. A cycle is complete only when the required code compiles, the focused tests pass, the user can explain the important syntax and equation-to-code mapping, and the retrospective companion section has been reviewed.
6. **Retrospective implementation companions:** After a cycle works and the user understands it, add a compact durable section containing the operation and equation, a short real usage example, only the essential implementation snippets, the equation-to-code mapping, the C++ terms encountered, validation and failure behaviour, frames and units, focused test meaning, and discovered limitations. Omit abandoned attempts, compiler transcripts, live status, duplicated source files, and generic language material unrelated to the implemented concept.
7. **Quality-gate cadence:** Do not invoke a C++ or Python quality-gate skill for teaching, terminology explanations, implementation-note drafting, routine learner-authored blocks, or ordinary focused compilation and tests. Invoke the applicable gate only at a stability checkpoint named in `CHECKLIST.md`, before capability closure, when the user explicitly requests it, or when a difficult defect requires a systematic audit.
8. **Necessity gate:** Add code only for a stated requirement that cannot be met more simply; avoid speculative features, abstractions, and dependencies.
9. **Traceability:** Ground every algorithmic or scientific component in a documented mathematical model. Trace infrastructure components to explicit engineering requirements.
10. **Design quality:** Keep modules single-purpose with clear names, types, units, assumptions, invariants, inputs, outputs, and failure behaviour. Keep configuration separate from logic.
11. **Test value:** Prioritise tests for project logic, requirements, edge cases, invariants, public contracts, integration boundaries, and previously observed defects. Do not test unchanged language or library behaviour, trivial data storage, generated boilerplate, or simple accessors unless they form a deliberate public contract or protect against a credible regression.
12. **Reproducibility:** Pin or document dependencies, control randomness, avoid hidden state, and record the configuration required to reproduce results.
13. **Operational quality:** Validate inputs, handle failures deliberately, use safe fallbacks, and add useful logging, telemetry, and timing information where operationally necessary.
